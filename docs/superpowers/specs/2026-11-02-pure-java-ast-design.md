# Pure-Java AST: design and first-phase prototype

## Intent

Replace the JNI wrapper for the Starlink AST library (jniast, in `../starjava/jniast`) with a pure-Java port.
Dropping JNI removes the per-platform native libraries, so applications ship as plain jars and new users can adopt AST without native-build pain.

Intended users:

- SPLAT-VO and astgui, the heaviest current users of jniast; they depend on `Plot`.
- The lighter current starjava users (frog, treeview, datanode, ndx, hds, sog).
- TOPCAT, which deliberately does not use jniast today because of JNI; a pure-Java AST removes that objection.
- Firefly (IPAC), mainly for reading FITS WCS headers (FitsChan) and pixel-to-sky transforms, and later YamlChan.

This document describes the long-term port briefly and the first phase, a prototype that proves the approach, in detail.

## Background

### jniast (the API to match)

- 68 public classes in `uk.ac.starlink.ast` (plus `grf` and `xml` subpackages), 265 native methods, about 10.5k lines of JNI C.
- The Java classes were generated by Perl scripts from the prologue comments of the AST C sources, and track roughly AST 5.1.
- The callbacks are already Java interfaces: `Grf` (with `DefaultGrf` drawing on Graphics2D), Channel source/sink, `Transformer` for IntraMap, and the resample/rebin kernels.
- `AstException extends RuntimeException` and carries an AST status code (`getStatus()`, `getStatusName()`).
- Licensed GPL; built with Ant at Java source level 1.8.

### The Rust port (the main source to port from)

- `../starlink-astrs` (repository name starlink-ast-rs), crate `crates/starlink-ast`: about 200k lines of source, including its own ports of ERFA, PAL and wcslib.
- Structure is cleaner than C; FitsChan in particular is split into one file per encoding (`src/fitschan/enc_*.rs`, `wcs_*.rs`).
- Class behaviour is modelled with traits (`Mapping`, `Frame`, `Region`) and an `AnyObject` enum for deserialised objects.
- Not ported: `Plot`, `Plot3D`, the Grf backends, `XmlChan`, `YamlChan`, `StcsChan`.
- Licensed LGPL-3.0-or-later.
- `docs/porting-hazards.md` records the mistakes that cost the Rust port most; the most expensive was collapsing C's per-class extension points, made twice.

### The C library (the final reference)

- `~/work/starlink-ast`, upstream `https://github.com/Starlink/ast`.
- The Rust port pins it as the submodule `reference/starlink-ast` at commit `3d3f255f`.
- `ast_tester/fixtures` holds language-neutral test data shared by the C and Rust repos (the Rust repo mirrors it in `crates/starlink-ast/tests/fixtures`).

### Test assets

- The Rust port has about 4,000 tests (2,851 integration, 1,222 unit) in about 142k lines of Rust.
- Language-neutral data under `ast_tester/fixtures`:
  - `wcsconv/inputs/`: 143 inputs, mostly FITS headers (`.head`), including SIP headers (`sip.head`, `sip2.head`, `sip-alt.head`, `sip-3d.head`, `sip-3d-swap.head`) and the LSST example FrameSet as a native dump (`lsst.ast`).
  - `wcsconv/framesets/`: native dumps of the FrameSet read from each input.
  - `simplify/`: about 880 native dumps of Mappings before (`.map`) and after (`.simp`) simplification.
  - `serialisation/`: native-format dumps used for read/write round trips.
  - `oracle/headers.oracle`, `oracle/framesets.oracle`, `oracle/simplify_fixtures.oracle`: forward and inverse transforms of sampled points for each fixture, generated by C (`gen_transform_oracle`); plain text, with the tolerances stated in each file's header.
  - `plot/`: 20 reference plots as SVG, for when Plot is ported.
- About 150 C probe programs in the Rust repo's `tools/oracle_fixtures/` print expected-value tables as Rust source (for example `lsst_probe.c` produces `tests/lsst_oracle/cases.rs`).

## Goals

Long term:

- A pure-Java AST in package `uk.ac.starlink.ast`, with class names and public method signatures as close as possible to jniast, so existing applications can swap jars with little or no code change.
- Behaviour that matches the current C library (the commit the Rust port pins), not the AST 5.1 that jniast was generated from.
- Classes that are in AST but not jniast (for example ChebyMap, Moc, Table, SplineMap) added later following jniast's conventions.

First phase (the prototype):

- Read the LSST example FrameSet and FITS-WCS headers, including SIP headers, into FrameSets, and transform pixel to sky and back with results that match C.
- A jniast-matching API for every class in scope, so application developers can examine it.
- Enough evidence for Tim and the SPLAT, TOPCAT and Firefly developers to decide whether to do the full port.

## Non-goals for the first phase

- Simplification beyond a pass-through (see Design).
- FitsChan writing, and reading any encoding other than FITS-WCS and native.
- Spectral and flux frames and their Mappings (SpecFrame, DSBSpecFrame, FluxFrame, SpecFluxFrame, SpecMap).
- Regions and STC.
- Resampling and rebinning.
- Plot, XmlChan, YamlChan.
- Performance tuning beyond what the Rust port already does: its structural speed-ups are ported, and transform speed is measured but not tuned.
- Being a drop-in replacement for any application.

## Anti-goals

- A public API that differs from jniast without a reason recorded in the code or this document.
- Expected values that come from running the Rust port; they must come from C.
- Heuristics, or widened test tolerances, that make results agree without an understood cause.
  A heuristic is allowed only where the original uses one, with a comment saying so.
- Any JNI or other native code.

## Decisions already made (Tim's)

- Port from the Rust port first; C is the final reference when they disagree or when Rust's structure is shaped by Rust itself.
- Package name `uk.ac.starlink.ast`.
- The prototype proves the FitsChan reading path; reading matters more than writing, because most use is displaying a FITS file someone was given.
- Regions are lower priority.
- Simplification does not change transform values (outputs agree before and after, to rounding); it matters for performance but not for transform correctness.
- Errors are Java exceptions, not a global status variable.
- No object is used by two threads at once; a thread that needs a FrameSet another thread uses makes its own copy.
- Plot comes later, after Tim ports it in the Rust port, and after FrameSet and FitsChan are in place.
- Success for the prototype: the jniast-matching API plus the core Frames and Mappings, for developers to examine.
- TimeFrame and TimeMap are in the first phase, because FitsChan turns MJD-OBS and DATE-OBS into a TDB epoch by converting between TimeFrames (C `ChooseEpoch`/`TDBConv`, Rust `fitschan/epoch.rs`), and most real headers carry a date.
- License LGPL-3.0-or-later.
- Java 8 is the baseline, agreed with the starjava developer, because about 30% of users still run Java 8 (see Java version).
- No test data is regenerated: the C probe output already committed in the Rust repo (`tests/*_oracle/cases.rs`) is converted to JSON for the Java tests.
- cminpack is ported from C rather than using Apache Commons Math, with a note in the port that Commons Math's `LevenbergMarquardtOptimizer` (a translation of the same MINPACK routine) could replace it later.
- The ERFA and PAL subset is ported from Rust, as the Rust port did, rather than using a third-party jar.
- Rust's structural speed-ups (whole-array loops, the NaN protocol, bulk kernels) are ported; its hardware-SIMD paths, which Java 8 cannot express, are ported as their scalar fallbacks and tagged `MODERN-JAVA`.
- `Frame extends Mapping` is kept because jniast's hierarchy needs it (FrameSet and later Region are Mappings); a plain Frame transforms as the identity, as in C, and nothing more of C's Frame-as-Mapping handling is ported.

## Constraints

- Pure Java with no runtime dependencies beyond the JDK.
- Java 8 language level and APIs (`--release 8`); the library runs on Java 8 and every later runtime.
- Licensed LGPL-3.0-or-later.
  jniast's hand-written Java is GPL and is not copied; its public signatures are matched, and implementations and documentation are written from the C (LGPL) and Rust (LGPL) sources.
  jniast's generated Javadoc text came from the AST C prologue comments, so documentation can be drawn from those prologues directly.
- Built with Maven; tests use JUnit 5, whose releases still run on Java 8 (JUnit 6 needs Java 17), so the whole suite can run on a Java 8 runtime as well as a current one.
- `mvn test` runs every test without needing the C library or the Rust toolchain.
- The test suite is run on both a Java 8 runtime and a current one, because the JIT's elementary functions (`Math.sin` and friends) may differ in the last bit between runtimes.
- Code layout, naming and formatting follow ordinary Java conventions; public names follow jniast.
- Environment found on Tim's Mac: no default JDK (`/usr/libexec/java_home` finds none), but Homebrew has OpenJDK 27 at `/opt/homebrew/opt/openjdk` and Maven at `/opt/homebrew/bin/mvn`.
  JDK 27's `javac --release 8` works but warns that the option is obsolete and will be removed in a future release, so builds should use a JDK that still supports it (a long-term-support JDK such as 21 or 25 is the safer pin).
  No Java 8 runtime is installed.

## Design

### Object model

- Class hierarchy as in jniast: `AstObject` → `Mapping` → `Frame` → `FrameSet`; `Frame` → `SkyFrame`, `CmpFrame`; `Mapping` → each Mapping class; `AstObject` → `Channel` → `FitsChan`; `AstObject` → `Axis` → `SkyAxis`.
- Rust traits become Java classes and overridable methods.
  Every per-class extension point in C (a virtual method a subclass overrides) stays an overridable method in Java, even where Rust merged it; see the Rust repo's `docs/porting-hazards.md`.
- Internal Rust enums become Java enums where the variants carry no data, and small class hierarchies where they do; see Java version for how `match` is translated.
- Shared versus copied objects follow C, not Rust.
  Java references behave like C pointers with the garbage collector doing the reference counting, so Java shares where C calls `astClone` and copies where C calls `astCopy`.
  For example CmpMap shares its components and records each one's Invert flag at construction (`cmpmap.c:4848`), while `FrameSet.addFrame` stores copies of the Frame and Mapping (`frameset.c:1427`).
  Rust copies everywhere because of its ownership rules, so this is one place to take behaviour from C.

### Memory

- The garbage collector replaces reference counting; there is no equivalent of `astAnnul`, `astBegin`/`astEnd` or `astExport`.
- jniast's `annul()` and `delete()` remain as deprecated no-ops so existing code compiles.
- `copy()` is a deep copy, like `astCopy`.

### Errors

- Every error is a thrown `AstException` carrying the same AST status codes jniast uses (from `ast_err.msg`), so code that catches `AstException` and checks `getStatus()` keeps working.
- Where C sets an error, tests it and clears it in order to try an alternative, Java uses `try`/`catch`.
- Problems FitsChan treats as warnings stay warnings, reported through the `Warnings` attribute and ASTWARN cards.

### Threading

- No locks in the library.
- An object may be used from any thread, but not from two threads at once; the class documentation says so and tells users to `copy()` a FrameSet per thread.
- Rust's `thread_local!` caches become `ThreadLocal`; caches held inside objects (`Cell`/`RefCell` fields in Rust, for example SkyFrame's sidereal-time and epoch caches) become ordinary fields.
- Global tables (for example the units tables) are immutable and initialised in a thread-safe way.

### Attributes

- String-based access (`set("A=v, B=w")`, `getC`/`setC`, `getD`/`setD` and the other typed forms, `test`, `clear`) works for every attribute of every class in scope, including axis-indexed names such as `Label(1)`.
- jniast's typed accessors (for example `getEpoch`/`setEpoch`) are present for the same attributes.

### Simplification

- In the first phase `Mapping.simplify()` returns a Mapping that transforms identically, without restructuring it.
- Internal callers (FitsChan reading calls simplify on the pixel-to-world Mapping; FrameSet frame conversion calls it too) go through the same method, so the real simplifier can be dropped in later.
- Because native dumps of read FrameSets depend on simplification, the first phase checks transform values, not dump text, for anything that C simplifies.

### First-phase scope

Classes, each with its jniast public API:

- `AstObject`, `AstException`, `Mapping`, `Frame`, `Axis`, `SkyAxis`, `SkyFrame`, `TimeFrame`, `CmpFrame`, `FrameSet`.
- Mappings: `UnitMap`, `ShiftMap`, `ZoomMap`, `WinMap`, `MatrixMap`, `PermMap`, `PolyMap` (including its iterative inverse), `CmpMap`, `SphMap`, `WcsMap` (every projection), `SlaMap`, `TimeMap`.
- `Channel`, reading and writing the native format (jniast's `toString()` and `show()` write through a Channel).
- `KeyMap`, which `Channel.warnings()` returns.
- `FitsChan`: card handling (`putFits`, `putCards`, `findFits`, `setFits`, `delFits`, `retainFits`, `purgeWCS`, the card cursor and iterator), encoding detection, and `read()` for the FITS-WCS and native encodings.

Supporting code ported as needed: the parts of ERFA and PAL that SkyFrame, SlaMap, TimeFrame and TimeMap use, wcslib's projections, AST's units handling, and PolyMap's `polyTran` fitting with the Levenberg-Marquardt solver it uses (SIP reading calls it; the Rust port has it in `poly_tran.rs`).
`lsst2.ast` needs a SplineMap and is deferred.

FITS-WCS reading covers every header in the fixtures whose FrameSet needs only the classes above, which includes SIP and the other polynomial distortions FitsChan turns into PolyMaps.
Headers needing anything else (spectral axes, `-TAB`, other encodings) are deferred.

jniast methods of in-scope classes that need out-of-scope work (for example `FitsChan.write()`, `Mapping.resample*()` and `rebin*()`) exist with their jniast signatures and throw `UnsupportedOperationException`.
Other jniast methods of in-scope classes, such as `mapBox()` and `decompose()`, are ported unless they need out-of-scope work.
jniast classes outside the scope are absent from the first-phase jar.

### Tests

- The C repo is a git submodule at `reference/starlink-ast`, pinned to the commit the Rust port pins, and tests read `ast_tester/fixtures` from it.
- Expected values come from C only: the oracle files directly, and tables produced by the C probe programs.
  Probe tables are the Rust repo's committed `cases.rs` files, converted to JSON.
- The Rust tests for each in-scope class are translated to JUnit as the class is ported.
- Every fixture and oracle section is accounted for: either in scope and tested, or named in a deferred list with the reason.
  A test fails if a deferred item starts passing, so the list stays accurate (the Rust port's `test_deferred_fixtures.rs` pattern).
- Tolerances are those stated by each oracle file or used by the corresponding Rust test.
  Java's `Math` functions can differ from C's libm in the last bit, as the Rust port found for SphMap (`test_lsst_oracle.rs`); any case needing a wider tolerance is listed with its measured size and cause, and fails if it becomes exact.
- The C oracles were generated with fused multiply-add contraction, which Java never applies implicitly; a row that differs for that reason (for example BAD on one side and finite on the other near a singularity) goes on the deferred list with that cause.
- Native round trip: reading an in-scope native fixture and writing it again reproduces it, with numbers compared to the same 4-ULP budget the C and Rust tests use.

### First-phase success criteria

1. Every public method of jniast's in-scope classes exists with the same signature, checked mechanically against jniast.
2. `lsst.ast`: forward and inverse transforms match C (the values from `lsst_probe.c`).
3. Every in-scope FITS header, including the SIP headers: pixel-to-sky and back match `headers.oracle`.
4. The in-scope sections of `framesets.oracle` and `simplify_fixtures.oracle` match.
5. In-scope native fixtures round-trip.
6. A short written report: what was ported, how long it took, what problems were found, which tolerances needed widening and why, and an estimate for the rest of the port.

## Later phases (indicative order)

1. Simplification, needed for speed and before FitsChan writing.
2. FitsChan writing and the other encodings (FITS-IRAF, FITS-PC, FITS-AIPS, FITS-AIPS++, FITS-CLASS, DSS).
3. Spectral and flux frames and their Mappings, which SPLAT needs.
4. The remaining jniast Mappings (LutMap, MathMap, TranMap, IntraMap, SwitchMap, SelectorMap, GrismMap, PcdMap, RateMap, DssMap) and KeyMap.
5. Resampling and rebinning.
6. Regions and STC.
7. Plot, after it is ported in Rust, behind jniast's `Grf` interface.
   jniast's `DefaultGrf` is GPL, so a Graphics2D implementation is either written afresh or relicensed by its authors.
8. YamlChan (for Firefly) and XmlChan, after they are ported in Rust.
9. AST classes that are not in jniast.

SPLAT and astgui can switch once phases 1–7 are done; Firefly's needs are mostly met by phases 1–2.

## Java version

The baseline is Java 8, agreed with the starjava developer, because about 30% of users still run Java 8.
Java 21 was considered; its main benefit for this port was that the compiler checks a `switch` over a sealed type handles every case, as Rust's `match` does, and the Rust source has 86 enums and over 900 `match` expressions.
The rules below keep as much of that safety as Java 8 allows, and mark the places a later Java would simplify.

### Translating Rust enums and `match`

- Where a `match` chooses behaviour by variant, prefer an abstract method on the variant classes, so the compiler makes every new variant implement it.
- A `match` on a data-free enum becomes a `switch` statement.
- A `match` that must test classes becomes an `instanceof` chain.
- Every `switch` has a `default`, and every `instanceof` or `if`/`else` chain that stands in for a `match` ends with a final `else`; that branch throws an `AstException` with status `AST__INTER` (internal programming error) naming the unexpected value.
  No branch silently ignores a value it does not expect.

### Marking where modern Java would simplify

- Code that a later Java would simplify carries a comment tag in the form `// MODERN-JAVA(21): <what would replace it>`, for example `// MODERN-JAVA(21): sealed interface with pattern-matching switch`.
- The tag goes on every `instanceof` chain or `switch` standing in for a `match`, every hand-written value class that would be a record, and anything else a newer feature would replace.
- `rg 'MODERN-JAVA'` lists every such place, so the code can be modernised if the baseline later rises.

### Other consequences of Java 8

- Small value types are final classes with final fields and hand-written `equals` and `hashCode`.
- No `var`, switch expressions, text blocks or `List.of`.
- No `Math.fma`; rows that differ from C because C used a fused multiply-add go on the deferred list (see Tests).
- No `strictfp` is needed: on the 64-bit x86 and ARM platforms Java 8 runs on today, HotSpot's default double arithmetic is already IEEE 754, and Java 17 made that the language rule (JEP 306).
- Users on newer runtimes still get the newer just-in-time compiler and garbage collector without any code change.

## Left to the builder

- Internal package structure (for example package-private helpers in `uk.ac.starlink.ast`, or internal subpackages for the ERFA, PAL and wcslib ports).
- Whether to use `Math` or `StrictMath` for the elementary functions.
- Which jniast Mapping and Frame methods FitsChan reading needs, beyond those listed.

## Porting rules

- Port from the Rust code; where Rust's structure comes from Rust itself (ownership, borrow-driven copies, trait objects), take the behaviour from C.
- Do not add heuristics or shortcuts the original lacks; when something does not match, find out why in the original.
- Keep C's per-class extension points as overridable methods.
- Read the Rust repo's `docs/porting-hazards.md`, `docs/issues/c-library-quirks.md` and `c-bugs.md` before starting.
