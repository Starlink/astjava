# Phase 6: rulings

These are the decisions made while executing the phase 6 plan ([`2026-11-18-pure-java-ast-phase6-resample.md`](../superpowers/plans/2026-11-18-pure-java-ast-phase6-resample.md)) where the plan was wrong, unclear or silent, or where the port departs from Rust, C or jniast or keeps a C quirk.
They are copied from the execution ledger (the controller's rulings and the user's decision) and from each task's report (the implementer's rulings), grouped by task; within a task the implementer's come first, in the order of the report, then the controller's, in the order they were made.
Each ruling gives what was decided, why, and what it costs if wrong.
A later ruling can reverse an earlier one; a ruling that a later one replaced carries a bracketed note saying so, and the rulings of a fix round follow the ones they replace.
There are 63 rulings, 57 by the implementers, 6 by the controller and the user.
The phase report is [`2026-11-18-phase6-report.md`](2026-11-18-phase6-report.md).

## Plan review

- User decision: `rebin` passes C `AST__USEVAR` when both `in_var` and `out_var` are given ("fix jniast for out_var so that it works properly"); jniast never set the flag, so through jniast C zeroed `out_var` and never filled it; with either array absent the flags and the arrays passed are jniast's, so an `outVar` given without `inVar` is left untouched, as jniast's JNI code passed C no `out_var` then — cost if wrong: a caller relying on jniast's zeroed output variances now gets rebinned ones.
- Ruling: the Gauss kernel is implemented in Task 2 although no public `Interpolator` reaches it — `Spreader.gauss` needs it in Task 3 and Rust's kernels module holds it — cost if wrong: none (moves code between tasks).

## Task 1: PixelArray, the resampling framework, nearest and linear

### Implementer

- Ruling: the inverse is fitted by `LinearApprox.linearApprox(map, ..., forward = false)` (transforming in the inverse direction) rather than C's `astInvert`/`astLinearApprox`/`astInvert` on the shared Mapping or Rust's copy-and-invert — Review Focus 4 requires concurrent resampling through one Mapping, and C's only `LinearApprox` is mapping.c's (no subclass overrides it), so the fit is the same — cost if wrong: none to values; a subclass that later overrides `linearApprox` would not be consulted for the inverse. [its reason was replaced by the controller's threading ruling: concurrent use of one Mapping is not supported; the fit stays, as it leaves the Invert attribute alone]
- Ruling: data and variance arrays must have exactly their grid's number of pixels (Rust's `!=`, AST__DIMIN, Rust's message prefixed with C's `astResample<X>(<class>): `) — the plan's Review Focus 2 says "does not match its grid" and the brief says Rust's checks — cost if wrong: a jniast caller passing a longer array (which jniast and C accept, and which the phase 1 ruling "longer arrays accepted as in C" would allow) now gets AST__DIMIN; switching to `<` is a one-line change in `Resample.checkLength`. [superseded in fix round 1: shorter arrays are an error, longer ones accepted]
- Ruling: a bound array shorter than its `ndim` is AST__DIMIN with Rust's message form ("1 input upper bounds supplied for 2 dimensions."), and a longer one is accepted — in Rust the slice length is the number of dimensions, here `ndimIn`/`ndimOut` are passed separately, as in jniast (which checked `<`) — cost if wrong: status and message only.
- Ruling: Rust's length checks sit where Rust puts them (bound arrays after C's dimension-count checks; data/variance lengths after C's bound, tolerance, region and flux checks, before simplification), so C's statuses win where both apply (the oracle's error cases with empty arrays get C's AST__GBDIN) — cost if wrong: which status a doubly-invalid call reports.
- Ruling: the AST__EXSPIX limit is a Java array's `Integer.MAX_VALUE` (the `TranGrid` precedent), with C's messages, including the output-grid message's two full stops — cost if wrong: the status of a grid too large for a Java array.
- Ruling: Rust's parameter-count check (`too_few_params_is_an_error`) is not ported and is listed in `deferred/rust-tests.txt` as Rust-only API — jniast's Interpolator factories always supply the parameters a scheme reads — cost if wrong: none.
- Ruling: `InterpolateNearest<X>` uses one general path for 1-D, 2-D and n-D, as Rust does — C's three paths do the same integer arithmetic — cost if wrong: none (oracle passes bit for bit).
- Ruling: the scheme dispatch's `default` throws AST__INTER "Unexpected sub-pixel interpolation scheme (n)." for the schemes Task 2 ports — the project rule for match-like defaults; C's AST__SISIN is for invalid integers jniast cannot construct — cost if wrong: until Task 2, sinc/somb/blockave/ukern1/uinterp give AST__INTER instead of resampling (never `UnsupportedOperationException`).
- Ruling: `ConserveFlux<X>` and `MatrixDet` are in Task 1, not Task 2 — the oracle's `conserve_zoom` linear case (a nearest/linear case of a jniast type) needs them — cost if wrong: Task 2 finds them already present.
- Ruling: the generic `resample` checks types with `instanceof` before calling `resample<X>` instead of catching `ClassCastException` around the call as jniast does; null `in` is `NullPointerException` (jniast's `in.getClass()`), a null `badval` is `IllegalArgumentException` (jniast: `NullPointerException` from unboxing) — so that an exception from inside the call (later a caller's `UinterpCalculator`) is never turned into the type message — cost if wrong: exception type for a null `badval`.
- Ruling: `PixelArray` has two methods the brief does not list, `copy(i, src, j)` (exact same-type copy; `get`/`set` through double would lose `long` precision above 2^53) and `set(i, v)` (C's `(Xtype) v`) — cost if wrong: none; Task 3 may extend further.
- Ruling: `signed()` is always true — every jniast type is signed; C's unsigned types are not ported (Global Constraints) — cost if wrong: none.
- Ruling: `ResampleSection`'s transform uses `Mapping.transform` (no Report output), since C's `astTransform` does not report (only `Tran1/2/N/P` call `ReportPoints`) — cost if wrong: none.
- Ruling: the NaN-bad-value behaviour (a NaN never equals a NaN `badval`, so no input is bad; output bad values are still NaN) is kept as C has it and recorded as a C quirk in `docs/rust-c-differences.md` — Review Focus 3 asks for C's output — cost if wrong: SPLAT/astgui callers see NaN propagate through linear interpolation exactly as with jniast.
- Ruling: data and variance arrays shorter than their grid give AST__DIMIN (Rust's message); longer ones are accepted with their leading elements used — controller ruling, phase 1 rule — cost if wrong: none known. [supersedes the exact-length ruling above]
- Ruling: concurrent resampling through one Mapping is not supported; threads each use a `copy()` — controller ruling, the spec's Threading section — cost if wrong: a caller sharing one Mapping across threads can get wrong results through simplification, as with any AST object. [supersedes the Review Focus 4 reading above]

### Controller

- Ruling: data and variance arrays longer than their grid are accepted (leading elements used), shorter ones give `AST__DIMIN` — the project's phase 1 rule (`docs/rust-c-differences.md` "Array arguments longer than needed"; C and jniast accept longer) outranks the plan's "does not match" wording — cost if wrong: one comparison in `Resample.checkLength`.
- Ruling: the plan's Review Focus 4 (two threads through one Mapping) contradicts the spec's Threading section ("An object may be used from any thread, but not from two threads at once ... tells users to `copy()` a FrameSet per thread"); the spec wins — `ResampleThreadsTest` becomes threads each resampling through its own `copy()` of one FrameSet (unsimplified `getMapping`), results equal to single-threaded and the original's dump unchanged; the Javadoc states the one-thread-at-a-time rule instead of promising concurrent use; the race the reviewer found (simplification's temporary in-place changes to shared components, as C makes) is use the spec rules out, so the Simplifier is not changed — cost if wrong: a later decision to support shared concurrent use needs the Simplifier and CmpMap reworked to stop changing shared components.

## Task 2: Kernels, block averaging, the caller's functions and flux conservation

### Implementer

- Ruling: `AST__GAUSS` is in the resampling dispatch and `ResampleKernels.setup`, and the `Interpolator` constructor is package-private so tests make it — C accepts the scheme, Task 3's `Spreader.gauss` needs the kernel, and jniast has no `Interpolator.gauss` (controller ruling) — cost if wrong: none to the public API (`JniastApiTest` green); the oracle's three Gauss case names run.
- Ruling: the oracle's error cases 13 and 14 expect `AST__UK1ER` and `AST__UINER` where C's probe recorded `AST__BADIN` — C passes on whatever status the caller's function sets; the probe's functions set `AST__BADIN`, jniast's callbacks set `AST__UK1ER`/`AST__UINER` — cost if wrong: status only; the test asserts C's recorded value is `AST__BADIN` before substituting.
- Ruling: a caller's `Exception` becomes `AstException` with jniast's status, C's context message only (as `IntraMap` does for its Transformer), and the exception as cause; an `Error` is not caught — Review Focus 1 — cost if wrong: message wording.
- Ruling: `UinterpCalculator` gets a copy of `offset` and new `int[]` bound arrays (jniast's `fuinterp<X>` makes new Java arrays for them), the caller's own data and output arrays (jniast passes those when C's pointers are the caller's), and the block's `coords` arrays themselves (jniast copies them; nothing reads them after the call) — cost if wrong: none observable except that a calculator writing into `coords` could see that array again in no later call (each block has new arrays).
- Ruling: `inVar` is given to a `UinterpCalculator` only when both variance arrays are given (C's `usevar ? in_var : NULL`); jniast would then build an array from C's null pointer — follow C — cost if wrong: a caller giving only `inVar` sees null.
- Ruling: `Kernel.value` declares no checked exception; the caller's kernel is an adapter that converts its exception — so Task 3's builtin kernels need no exception handling — cost if wrong: none.
- Ruling: `kval` arrays hold `min(2 * neighb, extent)` values per axis as Rust, where C allocates `2 * neighb` — no more than the extent is ever indexed — cost if wrong: none.
- Ruling: block averaging uses `long` indices where C's `InterpolateBlockAverage<X>` uses `int` (`(int) floor(x)`) — for coordinates beyond the `int` range both give an empty block and a bad pixel (C through `int` saturation and wrap-around) — cost if wrong: none known.
- Ruling: the kernels use `java.lang.Math` (project convention), and the 78 oracle cases whose kernels call sin, cos or exp fall back, where their hash differs, to a value comparison with a new C probe within derived bounds (D 1e-10, F 1e-2, integer types 1) — the plan's Gates and the controller's ruling; all 78 are in the probe so CI's x86-64 and Java 8 runtimes are covered, not only the 8 that miss here — cost if wrong: a D-only error below 1e-10 in those 78 cases would pass (F and integer cases of the same code pass bit for bit here). [superseded in fix round 1 by per-pixel bounds]
- Ruling: `tests/test_resample.rs::user_flags_reach_the_callers_interpolator_and_kernel` added to `deferred/rust-tests.txt` ("Rust-only API (the user flags AST__URESAMP1-4, which jniast's ResampleFlags lacks)") — brief — cost if wrong: none.
- Ruling: `tooFewParamsIsAnError` not translated (already in `rust-tests.txt` from Task 1) — controller ruling — cost if wrong: none.
- Ruling: the flags reach the interpolators as C's integer captured once per call, and the `ResampleFlags` object only reaches a `UinterpCalculator` — C works on its integer copy, jniast passes the object — cost if wrong: none (a calculator mutating the object changes nothing for the resampling).
- Ruling: `SombCos`'s halved factor and block averaging's one `bad_var` are kept and recorded as C quirks in `docs/rust-c-differences.md` — expected values come from C — cost if wrong: none (the oracle pins both).
- Ruling: the value comparison of the kernel cases uses a bound worked out per output pixel from its own weights instead of constants per type, and runs for every kernel case on every platform — the measured R reaches 33, which no useful global constant covers, and a per-pixel bound needs no assumption about R — cost if wrong: test-only machinery (`bounds`, `PositionRecorder`) mirrors `InterpolateKernel1<X>`'s blocks and bad pixels; a mismatch there would show as a failing bound, not a passing error. [supersedes the "`java.lang.Math` ... derived bounds (D 1e-10, F 1e-2, integer types 1)" ruling]

### Controller

- Ruling: `tooFewParamsIsAnError` (resample and rebin) is not translated — jniast's `Interpolator` and `Spreader` factories always build the parameters a scheme reads, so too few parameters cannot reach `resample` or `rebin`; Task 1 listed `test_resample_oracle.rs::too_few_params_is_an_error` as Rust-only API and Task 3 lists the rebin one the same way — cost if wrong: one small test.
- The controller accepted the implementer's per-pixel bound ruling of fix round 1 (above).

## Task 3: Rebinning

### Implementer

- Ruling: `rebin` passes `AST__USEBAD` when `usebad` and `AST__USEVAR` when both variance arrays are given — user's decision (Shared Design 3) — cost if wrong: none; with either array absent the result is jniast's.
- Ruling: the output variance array is passed to C only when the input one is given, as jniast's `Mapping.c` does, so `outVar` without `inVar` is left untouched (C, if given it, would zero it and set it bad under `wlim`) — follow jniast where the plan does not say otherwise; the Javadoc says so — cost if wrong: such a caller sees its array unchanged instead of zeros.
- Ruling: Rust's array checks (bound lengths, then data/variance lengths) come before C's checks and leave the output alone, as in Rust's `rebin` and jniast (both check before calling C); data/variance lengths are skipped when a grid's bounds are inconsistent (Rust's `grid_size`) — Rust puts them first for rebin (unlike resample) — cost if wrong: which status a doubly-invalid call reports, and whether out[0] is zeroed then.
- Ruling: shorter arrays give AST__DIMIN, longer ones are accepted with their leading elements used — controller ruling (phase 1 rule) — cost if wrong: none known.
- Ruling: after C's argument errors the first output value (and variance) is zeroed, as far as the array goes; after TRNND/BADFLG the whole output — C quirk Rust mirrors, `errorsMatchC` pins it — cost if wrong: a caller sees one zeroed value after an error.
- Ruling: C's AST__SSPIN check (`maxpix < 0`) is ported (Rust's `usize` cannot express it), with C's message and its place after PATIN — C is final — cost if wrong: none.
- Ruling: C's AST__BADFLG chain is ported with C's flag names, though only the oracle test can pass flags other than USEBAD/USEVAR — C's check of its argument — cost if wrong: none (unreachable through the public API).
- Ruling: `AST__CNFLX` and the flux result of `RebinAdaptively`/`RebinWithBlocking` are not ported, nor `conwgt`/`infac` multiplications (both are exactly 1 without `AST__PARWGT`/`AST__CONSERVEFLUX`, which Rebin<X> rejects), each with a comment naming the flag — Shared Design 5 — cost if wrong: none to values (multiplying by 1.0 and dividing 1.0 by sum are kept where they matter: `wgt = 1.0 / sum`).
- Ruling: `AST__GENVAR`/`AST__VARWGT` branches in the spreading functions are left out with comments — Shared Design 5 — cost if wrong: none.
- Ruling: an `int` output pixel adds each contribution in `int` arithmetic (wrapping) in all three spreading functions, as C (`out += CONV(IntType, c)` is `int + int`); Rust's nearest/linear go through `double` and saturate — C is final — cost if wrong: results differ only on overflow, which no case reaches; recorded in `docs/rust-c-differences.md`.
- Ruling: the variance is added as C's `out_var += CONV(var * pfac * pfac)`: the sum in double, converted to the type (saturating for int) — C's expression types — cost if wrong: none (oracle bit for bit).
- Ruling: `RebinSection`'s transform uses `Mapping.transform` (C's default, no NaN replacement), as Task 1 did; the oracle probe ran with `AST_REPLACE_NAN=1`, which makes no difference since Java's Mappings never output NaN — consistency with Task 1 — cost if wrong: none observable. [corrected in the final review: an IntraMap passed its Transformer's NaN outputs on until it was made to turn them into AST__BAD, as the Mapping class's contract requires; with that, the premise holds]
- Ruling: the scheme dispatch `default` throws AST__INTER ("Unexpected pixel spreading scheme (n).") rather than C's AST__SISIN — jniast's Spreaders cannot make another scheme (Task 1's precedent); C's `case 0:` (linear) is not ported for the same reason — cost if wrong: status only for an impossible scheme.
- Ruling: the `Spreader` constructor is package-private so tests make `AST__SOMB`/`AST__SOMBCOS`, as Task 2 did for `Interpolator`/`AST__GAUSS` — C accepts them and the oracle has `somb_unit` and `sombcos_win3` — cost if wrong: none to the public API (`JniastApiTest` green).
- Ruling: `Rebin` has a package-private `BlockSpreading` seam that replaces the spreading of each block when given; the oracle test records the blocks and output positions through it, as Task 2 recorded positions through a public `UinterpCalculator` — rebinning has no caller's function to observe positions, and without the exact positions no per-pixel bound can be worked out — cost if wrong: one package-private overload of `Rebin.rebin` and an interface; production passes null.
- Ruling: the 33 kernel probe cases (sin, cos or exp kernels, D/F/I) are compared value by value with `probes/rebin_kernel_probe.out` within a bound derived per output pixel in `RebinOracleTest.bounds` (kernel value differences as Task 2 derived them, propagated through reflection, box sums, weights, terms and the running sum; for `int`, one per term within its bound of a half-integer; sums of weights checked clear of `wlim`), on every platform, and `rebinningMatchesC` uses that comparison where a hash differs — controller ruling (Task 2's approach); `somb_unit` is excluded (J1's rational branch is plain arithmetic, passes bit for bit) — cost if wrong: the bound machinery mirrors `SpreadKernel1<X>`'s boxes and reflection in test code; a mismatch would show as a failing bound.
- Ruling: `tooFewParamsIsAnError` not translated; `tests/test_rebin_oracle.rs::too_few_params_is_an_error` listed in `rust-tests.txt` — controller ruling — cost if wrong: none.
- Ruling: Rust's `RebinValue::square`/`sub_square` are not added to `PixelArray` (the brief lists them) — only `RebinSeq<X>`'s `AST__GENVAR` and normalisation use them, which are not ported, and dead code would be untested — cost if wrong: a later RebinSeq port adds two methods.
- Ruling: `RebinOracleTest.mapping` uses Rust's rebin probe Mappings (forward formulas for `nonlin2`, `cubic1`, `nonlin3`, and `noforward`), which differ from the resample probe's — the rebin probe source — cost if wrong: none.

The review verified the `outVar`-without-`inVar` ruling against jniast's `Mapping.c`, which fetches `out_var` only when `in_var` is given.

## Task 4: The remaining Rust tests, the deferred sweep and a differential run against C

### Implementer

- Ruling: the 14 `test_rebinseq*.rs` tests are listed with the reason `astRebinSeq (not in jniast)` — Shared Design 5 — cost if wrong: none (a later RebinSeq port translates them).
- Ruling: `rust-tests.txt` has no automated checker, so unlisted Rust files are found only by sweeps; not changed — the brief forbids changing the checker's design without a Ruling, and that is a phase-level decision — cost if wrong: a Rust test file can stay neither translated nor listed (as `test_huge.rs` is) until someone sweeps.
- Ruling: `tests/test_huge.rs::huge` is not listed here — the brief allows only the six files' tests to change the lists — cost if wrong: one unlisted Rust test, reported for the phase report. [superseded by the controller's ruling: listed in Task 5]
- Ruling: the differential run's MathMaps use only arithmetic and `sqrt` (correctly rounded in both), so every Mapping and fit is bit-identical and positions are C's; transcendental MathMaps are excluded — the per-pixel bounds assume identical positions (as the oracle tests do), and a position differing in the last bit can change which pixels a kernel reaches, which no bound covers — cost if wrong: Mapping-induced differences are not exercised by the run (they are Mapping behaviour, gated elsewhere).
- Ruling: somb and sombCos are generated only with reaches of at most 2 pixels, where J1 uses its rational approximation (plain arithmetic: somb compared bit for bit, sombCos within the 6u kernel bound); J1's asymptotic branch (sin, cos, sqrt with cancellation) has no relative error bound — as `RebinOracleTest.kernelDifference` asserts — cost if wrong: Somb with npix ≥ 3 is not differentially checked.
- Ruling: flux-conservation bounds use the factor measured from Java's own run of the same sections (ones resampled by nearest), and the integer bound |F| + 1 — the factor is plain arithmetic and so C's; the bound is derived above — cost if wrong: a factor bug would show as an exact-scheme failure first, since nearest/linear/blockAve conservation cases are compared bit for bit.
- Ruling: rebin with only one variance array (Java leaves `outVar` untouched or passes no variances) is not in the run — `RebinJniastTest` covers those calls against C's probe — cost if wrong: none known.

### Controller

- Ruling: `tests/test_huge.rs::huge` (the port of `testhuge.c`; needs Polygon and Moc Regions and about 45 GB grids) is listed in `rust-tests.txt` in Task 5's commit with a Regions reason, since `rust-tests.txt` has no automated checker and an unlisted test would be silently lost — cost if wrong: one line.
